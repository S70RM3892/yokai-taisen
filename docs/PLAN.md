## 0. 大前提：IP（権利）の扱い

妖怪ウォッチはレベルファイブの IP。**キャラ名・デザイン・固有名詞（ニャン、とりつき、えんら 等）はそのまま使えない。**
ゲームの仕組み（ルール）そのものは著作権で保護されにくいが、見た目・名称・テキストは保護される。

- 方針：**システムの面白さだけを継承し、キャラデザイン・名称・テキストはすべてオリジナル**にする。
- 「妖怪」というテーマ自体と、民間伝承の妖怪（河童・天狗・雪女など）は誰のものでもないので使ってよい。
  ただし**原作のキャラクター（ジバニャン等）の見た目・名前・ダジャレ的な命名の仕方はまねしない**。
- 本ドキュメント内の原作用語は「分析用の参照」であり、製品には出さない。

## 1. 原作（YW2）対戦システムの分析

### 1.1 確認できた仕様（出典付き）

| 要素 | 仕様 | 出典 |
|---|---|---|
| 編成 | 6体。前衛3体が戦い、後衛3体は待機 | Game8, Gamer Guides |
| ウォッチ回転 | 円形の編成を回して前衛/後衛を入れ替える | Game8, Wikipedia(EN) |
| 自動行動 | 妖怪は攻撃・妖術・ガード・とりつきを**自動で**選ぶ。プレイヤーは直接命令しない | Gamer Guides |
| 必殺技 | 妖気ゲージが満タンで発動。**プレイヤーが出せる唯一の攻撃命令**。発動時にタッチのミニゲーム | Game8, Gamer Guides |
| 妖気の溜まり速度 | 妖怪ごとに差があり6段階。装備（たましい）で調整可能 | たくトンボ(note) |
| 行動順 | 素早さ依存。「行動ポイント」という内部値あり。初期前衛は初動が速い | たくトンボ(note) |
| とりつき | 味方にバフ、敵にデバフ。性格で対象選択が変わる | Game8, たくトンボ |
| おはらい | とりつかれた妖怪を後衛に回し、ミニゲームで解除 | Game8, Gamer Guides |
| ねらう | ピンを刺した敵に集中攻撃させる | Gamer Guides |
| アイテム | 戦闘中に使用可、使用後に短いクールダウン | Gamer Guides |
| 種族ボーナス（陣） | 前衛に同種族を揃えるとステ補正 | hrs-game |
| 対戦ランク | ランダム対戦は公式ルール。ポイントでランク決定 | Game8, 攻略大百科 |

### 1.2 なぜ面白かったのか（設計上の核）

1. **「間接操作」なのに読み合いが深い**
   直接攻撃命令を出せない。プレイヤーの仕事は「誰を前に出すか」「いつ必殺技を切るか」「いつ回して守るか」。
   → 操作量は少ないが、**判断密度は高い**。
2. **リアルタイム × 自動行動 = ATB的な緊張感**
   ターン待ちがない。回すタイミング、ゲージの溜まりを常に見る必要がある。
3. **ローテーションが攻防一体**
   回す＝傷ついた妖怪を逃がす／おはらい／ゲージを溜めた妖怪を前へ／陣を組み替える。1操作に複数の意味。
4. **とりつきによる非ダメージ干渉**
   殴り合いだけでなく「相手の編成を腐らせる」軸がある。
5. **ミニゲームによる実行力要素**
   必殺技・おはらいに手先の技術が乗る（ただし対戦ではノイズでもある → 後述）。

### 1.3 原作の弱点（現代化で直すべき点）

- ~~**ランダム性が強すぎる**：自動行動・なまけ等で運負けが多い。競技性が低い。~~ → 検討の結果、**乱数は原作どおりにする**（§7 の 7・19）。ダメージの揺れだけ小さくした。
- **情報が見えない**：行動ポイント・妖気速度など重要値が隠しパラメータ。
- **ミニゲームが対戦を遅くする**：必殺技のたびに下画面操作。観戦にも向かない。
- **バランス調整が不可能**（パッケージ買い切り時代）。
- **オンライン体験が貧弱**：3DS通信、観戦・リプレイなし。

## 2. コンセプト

**「指揮官として戦う、3v3 リアルタイム・ローテーションバトル」**

- 1試合 **3〜5分**。スマホ／PC／Switch系で遊べる。
- プレイヤーは「駒を直接動かさない指揮官」。操作は少ない、判断は重い。
- **読みと判断** で勝敗が決まる競技性。乱数は原作どおり残し、それへの対応（回転・浄化・つつき）で腕の差が出るようにする。

### ターゲット
- ポケモン対戦・クラロワ・オートバトラー層の中間。
- 「アクションは苦手だが頭で勝ちたい」層。

## 3. コアルール（概要）

> ここは概要だけ。**詳しい数値とルールは `BATTLE_SPEC.md` が正**。食い違ったら BATTLE_SPEC に合わせる。

### 3.1 編成
- 6体 × **ホイール**（円形）。上3体が前衛。
- 回転は時計回り／反時計回りの2方向。
- **回転の待ち時間は 3 秒**（原作の公式ルールの「3秒ルール」）。連打回しはできない。

### 3.2 自動行動
- 各ユニットは **行動ゲージ（見える化）** が溜まると行動。
- 行動は「通常攻撃／スキル／ガード／呪付（とりつき相当）」から AI が選ぶ。
- **性格＝行動の確率**：8種から自由に選ぶ。行動は毎回ランダム（原作どおり）。詳細は `BATTLE_SPEC.md` §4.2。

### 3.3 必殺技（仮称：奥義）
- 奥義ゲージ満タンで発動。**唯一の直接命令**。
- 原作のミニゲームの代わりに **溜め（0〜2 秒）＋タイミング判定** のスキルチェックにする（観戦しやすく、入力差で勝敗が決まりすぎない）。構えは相手に見えるので、相手は回して避けられる。
- 構えは同時に1体まで。3体分の妖気で撃つ **大奥義**（原作の G技）もある。

### 3.4 呪付／浄化（とりつき・おはらい）
- 呪付：味方バフ or 敵デバフ。敵の前衛に付いたら、**相手は回して後衛で浄化するしかない**。
- 浄化：後衛で 2 秒かかる（ミニゲームなし、時間コスト制）。
- → 「浄化するために回す」と「前衛が薄くなる」のジレンマが核。

### 3.5 標的指定（ねらう）
- 敵1体にピン。自軍の自動攻撃が集中。切り替えにクールダウン。

### 3.6 つつき
- 呪付のかかった敵・なまけている敵を連打して、妖気を奪う（原作の零式の「つつく」）。つついている間は他の操作ができない。

### 3.7 陣（種族ボーナス）
- 前衛に同系統を2〜3体揃えるとボーナス。
- 回転で陣が崩れる／組まれる → 回転の意味がさらに増える。

### 3.8 装備
- 戦闘中に使うアイテムはなし。1体に1つ装備を持たせ、試合中ずっと効く（`BATTLE_SPEC.md` §8.3）。

### 3.9 勝利条件
- 相手6体全滅 or 制限時間終了時に残HP割合で判定。

## 5. 技術方針（案）

### 5.1 決定論シミュレーション
- 戦闘ロジックを **固定ティック（例：20tick/秒）+ 固定小数点 or 整数演算** で書く。
- 同じ入力列 → 同じ結果。リプレイ・チート検出・ロールバックが楽。

### 5.2 構成
```
[クライアント(描画・入力)] ⇄ [対戦サーバ(権威、シミュ実行)] ⇄ [マッチング/レート/DB]
          ↑ 共通の戦闘コアライブラリを両方で使う ↑
```
- 入力は「回転」「奥義」「標的」「浄化」「つつき」の5種類だけ（`BATTLE_SPEC.md` §11）→ 通信量が非常に小さい。
- **サーバ権威型**（入力のみ送信、結果はサーバが確定）。

### 5.3 技術スタック候補
| 選択肢 | 長所 | 短所 |
|---|---|---|
| **TypeScript（戦闘コア）+ Web（PixiJS/Phaser）+ Node サーバ** | 1言語でクライアント/サーバ共通化。ブラウザで即遊べる。プロトタイプ最速 | 3D・ネイティブ性能は弱い |
| Godot 4 + GDScript/C# | 無料・軽量・マルチプラットフォーム | サーバとのロジック共有に工夫が要る |
| Unity + C# | 実績・アセット豊富 | ライセンス変動リスク、重い |
| Rust（コア）+ WASM | 決定論と性能が強い | 学習コスト大 |

**推奨：まず TypeScript で戦闘コア + ブラウザ版プロトタイプ。** 面白さの検証が最優先で、描画は後で差し替え可能。

## 8. キャラの量

### 決まったこと
- **公開時は48体**（8種族×6体）。
- **種族ごとのランクの比率は S：A：B ＝ 1：1：2**。S は少なく特別にする。B を多くして、重複で陣を組めるようにする（チームに入れられるのは S・A それぞれ2体までなので、B が編成の中心になる）。
- 絵はまだ決めない。

### 公開時の数：48体（決定）
種族は原作どおり8種族にした（`BATTLE_SPEC.md` §9）。1種族6体だと 1：1：2 は種族ごとには割り切れないので、**全体で比率を守る**。
| 種族 | 1種族あたり | 全体 |
|---|---|---|
| 4種族 | S2・A1・B3 | S8・A4・B12 |
| 残りの4種族 | S1・A2・B3 | S4・A8・B12 |
| 合計 | | **S12・A12・B24**（1：1：2） |

### 増やし方
キャラが増えるほど重くなるものが3つある。
1. **デザイン**：オリジナルの絵が1体ずつ要る（一番お金と時間がかかる）。
2. **バランス調整**：キャラ同士の組み合わせは、キャラ数のほぼ2乗で増える（12体 → 66通り、24体 → 276通り、36体 → 630通り、48体 → 1128通り）。
3. **覚える量**：相手のキャラを知らないと読み合いにならない。

そこで、**一度に全部作らず、12体ずつ段階的に増やす**。
| 段階 | 体数 | 1種族あたり | やること |
|---|---|---|---|
| P1〜P2 | 12 | — | 今の12体で、面白いかを確かめる（8種族のうち祟・鎮はまだユニットがいない） |
| P4 前半 | 32 | 4（S1・A1・B2） | 8種族そろえた比率どおりのセット。シミュレーターで調整する |
| P4 後半 | 48 | 6 | 公開時の数。足すたびにシミュレーターで確認する |
| 公開後 | ＋8／シーズン | ＋1 | 1種族に1体ずつ足して、環境を動かす（格闘ゲームの年ごとの追加と同じ考え方） |

- 参考：スト6 は発売時18体で、毎年4体ずつ足して3年目の終わりに30体。クラロワはカードが120枚以上ある。
- 今の12体のランクと種族（`UNITS.md`）は仮。32体に増やすときに、比率と8種族に合わせて振り直す。

### キャラを足すときの決まり（案）
- 役割（アタッカー・壁・支援・妨害・速攻）が種族の中で偏らないようにする。
- 属性の弱点と耐性が、全体で偏らないようにする。
- 新しいキャラは、今いるキャラの完全な上位互換にしない。

## 9. 演出（モーション・BGM・効果音）

### 9.1 いつ作るか
| 段階 | モーション | 音 |
|---|---|---|
| P1 | なし（CLI だけ） | なし |
| P2 | 四角が揺れる・光る・数字が飛ぶ程度（CSS か GSAP） | 効果音だけ、フリー素材で仮置き。BGM はなしか、フリー素材で仮置き |
| P3〜P4 | 読み合いに必要な演出を固める（§9.2） | 仮のまま |
| P5 | 絵と一緒に本番の演出を作る | 本番の BGM・効果音を決める |

### 9.2 モーションの決まり（ゲームのルールから来る制約）
- **演出は画面だけのもの**。戦闘の中身（tick の進み方）を待たせない。演出が長くても、戦闘は止まらない。
- 前衛6体がそれぞれ 2.5〜5 秒に1回動く（`BATTLE_SPEC.md` §4.1）ので、**通常攻撃・術のモーションは 0.5〜1 秒** に収める。重なっても見分けられる動きにする。
- **読み合いに必要な情報を、一番はっきり見せる**：なまけ中、相手の構え・大奥義の構え、つつかれていること、呪付・加護がかかった瞬間。ここは派手さより「ひと目でわかる」を優先する。
- 奥義・大奥義だけは長い演出にしてよい。ただし戦闘は止めない。長さは溜め＋解放の時間の中に収める。
- 観戦とリプレイでも同じ演出が出るように、演出は「戦闘の状態とイベント」から作る（入力からではない）。

### 9.3 作り方の候補
**モーション**
| 方法 | メモ |
|---|---|
| GSAP（Web のアニメーションライブラリ） | 2025年4月から、全プラグインを含めて商用でも無料 |
| スプライト（コマ送りの絵） | 絵の枚数が増える |
| Live2D | 直近の年間売上が 1,000 万円未満なら、商用でも出版許諾契約は不要 |
| Spine | 2D の骨入れアニメ。有料 |

**BGM・効果音**
| 方法 | メモ |
|---|---|
| フリー素材（例：魔王魂、DOVA-SYNDROME） | 無料・商用可。魔王魂は CC BY 4.0 で、クレジット表記が必要。DOVA は「音楽が主役のゲーム」では使えない。**使う前に各サイトの規約を必ず読む** |
| 作曲を依頼する | 一番確実。お金と契約が必要 |
| 音楽生成 AI（例：Suno） | 有料プランなら商用で使えるが、著作権が自分のものになるとは限らない。レコード会社との裁判も続いている。本番に使うかは慎重に決める |
| 原作の BGM・効果音 | **使わない**（権利がない） |

- ブラウザは、プレイヤーが一度画面を触るまで音を鳴らせない。タイトル画面で「タップして開始」を挟む。
- 音は戦闘の読み合いにも使う（相手の構え・大奥義の構えの音など）。音を消していても遊べるように、同じ情報は必ず画面にも出す。

### 9.4 まだ決めていないこと
- 本番のモーションの作り方（絵の方式と一緒に P5 で決める）
- 本番の BGM を誰が作るか
